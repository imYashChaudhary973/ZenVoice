# Update — July 2026

[02-research.md](02-research.md) called a Hinglish-native model "medium-high
risk, entirely on conversion", because no GGML build existed and the
safetensors→GGML path was a known rough edge. **That is no longer true.** This
document records what changed and what it means for the plan.

## 1. The blocker is gone, and there is a better model than the one we picked

Oriserve shipped **Whisper-Hindi2Hinglish-Apex** after our survey was written.
It is the same family as Prime but built on a different base:

| | Prime | **Apex** |
|---|---|---|
| Base model | whisper-large-v3 | **whisper-large-v3-turbo** |
| Parameters | 1,543.5 M | **808.9 M** |
| Downloads | 278.8 K | 151.9 K |
| License | Apache 2.0 | Apache 2.0 |
| Output script | Romanized Latin | **Romanized Latin** |

Apex is the right one for ZenVoice, not Prime. It is turbo-derived, so it lands
in the size and latency class we already ship and already recommend as the
default on Apple Silicon:

| Build | Size | Compare to catalog |
|---|---|---|
| `ggml-apex-hinglish-q5_0.bin` | 574 MB | `whisper-large-v3-turbo` q5_0 is 574,041,195 B |
| `ggml-apex-hinglish-q8_0.bin` | 874 MB | — |
| `ggml-apex-hinglish-fp16.bin` | 1.62 GB | — |

The q5_0 size matching our existing turbo entry almost exactly is the
confirmation that this is architecturally the same model we already run.

Reported WER against stock large-v3:

| Dataset | large-v3 | Apex | Prime |
|---|---|---|---|
| Common Voice | 61.94 | 35.96 | 32.43 |
| FLEURS | 50.84 | 29.79 | 28.68 |
| IndicVoices | 82.56 | 47.64 | 60.82 |

Prime is modestly better on the two clean benchmarks; Apex is **13 points
better on IndicVoices**, the hardest and most natural-speech of the three, at
half the parameter count. Trained on ~700 h of noisy Indian-accented Hindi.

### GGML conversions now exist

Three community conversions are published:

- [`Marquestra/Whisper-Hindi2Hinglish-Apex-GGML`](https://hf.co/Marquestra/Whisper-Hindi2Hinglish-Apex-GGML) — fp16 / q8_0 / q5_0
- [`voquill/whisper-hindi2hinglish-apex-ggml`](https://hf.co/voquill/whisper-hindi2hinglish-apex-ggml)
- [`curiophile/whisper-hindi2hinglish-ggml`](https://hf.co/curiophile/whisper-hindi2hinglish-ggml) — Prime

**Do not ship these directly.** All three report zero downloads and none is
from the model author. Their value is as *proof the conversion works* — the
risk [02 §4](02-research.md#4-integration-huggingface--whispercpp) was written
about has been retired by demonstration. Since the catalog pins `sha256` for
every model, ZenVoice should run the conversion itself and pin its own artifact
rather than trust an unattributed third party.

**Phase 2a therefore drops from a two-day spike with a real chance of failure
to a conversion run plus a catalog entry.**

## 2. The defect is still live

Re-ran `tools/translit-check.swift` on 2026-07-25 against current `main`:
still 8/8 wrong, still `computer → कंप्यूटर → kampyutara`. Nothing in the
intervening work touched `LocalTransliterator`, and Findings
[1](01-diagnosis.md#f1) and [2](01-diagnosis.md#f2) stand unchanged.

## 3. Mixed-script models — a second architecture worth knowing about

Two newer models emit **mixed script**: Hindi words in Devanagari, English
words left in Roman.

- [`Trelis/Whisper-Hinglish-Preview`](https://trelis.substack.com/p/whisper-hinglish)
  — injects a `<|mixedcode|>` token after the language token; without it the
  model collapses to a single script. Built on ArtPark's Vani base.
- [`shunyalabs/zero-stt-hinglish`](https://huggingface.co/shunyalabs/zero-stt-hinglish)
  — Whisper Medium post-trained, 0.8 B, Open RAIL license.

This is worth noting because of how it interacts with our code.
`LocalTransliterator.latinScript` already segments the string into native-script
runs and only transforms those. A mixed-script model would therefore have its
English words **pass through untouched** and only its Hindi words romanized —
[Finding 2](01-diagnosis.md#f2) would be fixed with no change to the
transliterator at all, leaving only the schwa/diacritic quality problem, which
is far more tractable once it is restricted to genuinely Hindi words.

It remains the fallback, not the plan. The `<|mixedcode|>` token is a custom
special token, and whisper.cpp's tokenizer handling of non-standard special
tokens is an unknown we would have to spike. Open RAIL is also a redistribution
question Apache 2.0 does not raise.

## 4. What must be measured before adopting Apex

The model card states no limitations at all, which is itself a reason for
caution. Specifically unverified:

- **English-dominant Hinglish.** Training data is Hindi-dominant. A technical
  user saying "the pull request ka status kya hai" is mostly English.
- **Pure English.** If a user leaves the Hinglish profile selected, output
  quality on English must not collapse.
- **Hallucination on silence**, which the noisy training data makes plausible.

### The harness cannot currently detect the bug it needs to detect

`ZenVoiceAccuracyChecks` asserts only that Hinglish output *contains no
Devanagari*. That is a property check, and it is passed equally by:

- `kampyutara par kama kara raha hum` — the current, broken output
- `computer par kaam kar raha hoon` — the desired output

Apex would pass it trivially on day one while telling us nothing. Before
adopting any Hinglish model the harness needs a **loanword-preservation rate**:
fixtures containing known English words, scored on whether those words come back
as English. That single metric captures [Finding 2](01-diagnosis.md#f2), which
is the defect that actually matters, and unlike WER it is not defeated by
Hinglish having no canonical spelling.

### Baseline, measured 2026-07-25

That metric now exists in `ZenVoiceAccuracyChecks`. Measured on Whisper Medium
against synthesized code-switched audio:

```
  hin-status@170wpm               0/3      0%   lost: project, status, email
  hin-status@260wpm               0/3      0%   lost: project, status, email
  hin-server@170wpm               0/3      0%   lost: server, down, wait
  hin-server@260wpm               0/3      0%   lost: server, down, wait
  hin-meeting@170wpm              0/3      0%   lost: meeting, file, download
  hin-meeting@260wpm              0/3      0%   lost: meeting, file, download
  hin-review@170wpm               0/4      0%   lost: pull request, review, computer, test
  hin-review@260wpm               0/4      0%   lost: pull request, review, computer, test
  ------------------------------------------------------------
  OVERALL                        0/26      0%
```

**0 of 26.** Not one English word survived, at either speaking rate. Sample
output:

```
  प्रोजेक्ट का स्टेटस क्या है      →  prujika ka stetasa kya hai
  सर्वर डाउन है                    →  sarvara da'una hai
  प्रिया ने पुल रिक्वेस्ट रिव्यू किया →  priya ne pula rikvesta raviyu kiya
```

Two things this confirms that the standalone `translit-check.swift` could not.
First, the failure survives the full pipeline on real decoded audio, not just a
transliteration of hand-written Devanagari. Second, and more usefully: every one
of those clips **passed the existing "no Devanagari remains" assertion**. The
harness was reporting a clean Hinglish run while losing 100% of the English
vocabulary, which is precisely the blind spot this metric closes.

The measurement is self-verifying — the harness scores a known-good and a
known-broken string first and fails if it cannot tell them apart, so the zero is
a finding rather than a stuck counter.

A floor is now asserted, but **only for a model that declares
`.hinglish`**: fewer than 18 of 26 preserved fails the run. A general
multilingual model still scores 0/26 and is not failed for it, because that gap
is the defect a Hinglish model exists to fix rather than a regression.

The floor was verified by raising it above the measured score and confirming the
run fails — a threshold that has never been seen to fail is not evidence of
anything.

## 6. Apex, converted and measured — 2026-07-25

The conversion was done locally rather than taken from a community repo, so the
artifact ZenVoice would pin is one we produced. torch and transformers were not
needed: upstream's `convert-h5-to-ggml.py` loads the checkpoint through
`WhisperForConditionalGeneration` only to reach `.state_dict()`, and reading the
safetensors file directly reaches the same tensors under the same names. The
port lives in the scratch tree; the tensor mapping, header layout and dtype
rules are copied from upstream unchanged.

Result: 587 tensors, 1.62 GB f16 — byte-for-byte the same size as the published
community conversion.

### It clears the gate

| | Whisper Medium | **Apex** |
|---|---|---|
| Loanword preservation | 0/26 (0%) | **21/26 (81%)** |
| English dictation WER | **2.0%** | 16.8% |

Sample output, against the "what a person would write" column of
[01-diagnosis.md](01-diagnosis.md):

```
  mujhe meeting mein jaana hai. yah file download kar do.
  thoda sa wait karo.
  mainne email bhej diya.
```

That is the target representation, produced directly, with no transliteration
step involved.

The five remaining losses are informative rather than random: `server` comes
back as `sarvar`/`sarbar` (romanized Hindi pronunciation rather than the English
word), and `pull request` as `full request` — the same minimal pair the English
fixtures were built to catch.

### The conversion is faithful

The independently-produced `Marquestra` q8_0 build scores **identically** —
16.8% English WER, 21/26 loanwords, 18.5% segmented. Two conversions by
different people agreeing to the digit is good evidence that neither is subtly
wrong. It also settles the quantization question for this model: **q8_0 costs
nothing measurable against f16**, so the 874 MB build is the one to ship, not
the 1.62 GB one.

### It must never be a general default

Apex scores **16.8% on English dictation against Whisper Medium's 2.0%** — an
eightfold regression. It does not merely mishear; it dissolves technical
English:

```
  "The Kubernetes cluster is throttling"  →  "Cluster is traveling"
  "idempotent requests"                   →  "I don't want requests"
  "stale endpoint slice"                  →  "stay on point slice"
```

This is exactly the risk the model card declines to mention, and it is why
`.hinglish` is its own capability rather than a second kind of `multilingual`.
`isCompatible` admits it for the Hinglish profile and refuses it everywhere
else, and `ZenVoiceCoreChecks` asserts both directions.

### Two integration details that are not optional

**Decode under the English token.** Oriserve run Apex with `language="en"`, and
that is what makes the output Latin. Passing `hi` puts it back into Devanagari
and undoes the entire feature. `whisperLanguageArgument(for:)` now depends on
the model capability for this reason.

**Do not romanize its output.** `LocalTransliterator` is skipped when the model
emits Latin natively — running it over already-correct text would only damage
it.

## 7. Found while integrating: push-to-talk loses the first word

Apex was dropping the opening word of most fixtures. It is not a conversion
fault and not specific to Apex — it is that dictation audio begins on the first
syllable, and the encoder has no lead-in. The same clip, padded:

```
  no padding     "Ka status kya hai? Mainne email bhej diya."
  0.5 s padding  "Project ka status kya hai? Mainne email bhej diya."
```

Word error rate on that clip halves, 22.2% → 11.1%. ZenVoice is push-to-talk,
so every real dictation starts this way.

`WhisperDecoding.withLeadInSilence` now prepends 0.5 s before decoding. It is
free: whisper.cpp pads every input to its 30-second window regardless, so this
moves where speech sits in a window that was going to be filled anyway.

Measured across models on the release path, which decodes the whole recording:

| Model | whole, before | whole, after |
|---|---|---|
| Apex | 20.9% | **16.8%** |
| Whisper Medium | 2.0% | 2.0% |
| Whisper Base (en) | 5.4% | **4.7%** |

Apex loanword preservation also rose, 20/26 to 21/26. One regression worth
recording honestly: Base's *segmented* score worsened, 5.4% → 7.1%. Segmented
decoding is the diagnostic path rather than the release path — the app commits
the whole recording — but it is a real number and should not be buried.

## 8. Shipping state

The catalog entry exists and resolves:

| | |
|---|---|
| Catalog id | `hindi2hinglish-apex` |
| File | `ggml-hindi2hinglish-apex-q8_0.bin`, 874,188,075 bytes |
| sha256 | `0b4324d2…c28c719` |
| Capability | `.hinglish` — Hinglish profile only |
| License | Apache-2.0, redistributed with attribution |

The weights were converted here rather than taken from a third party, then
quantized with whisper.cpp v1.9.1's own `whisper-quantize` at the version the
app links. Three artifacts were measured and all agree exactly — 21/26
loanwords, 16.8% English, 18.5% segmented:

| Artifact | Result |
|---|---|
| our f16, 1.62 GB | 21/26 · 16.8% |
| our q8_0, 874 MB | 21/26 · 16.8% |
| community q8_0, 874 MB | 21/26 · 16.8% |

Our q8_0 and the community build are the same size to the byte but differ in
checksum, so they are independent files that behave identically. q8_0 is what
ships: half the download, no measurable cost.

### Published and verified end to end

The converted weights live at
[`imYChaudhary22/zenvoice-hinglish-apex-ggml`](https://huggingface.co/imYChaudhary22/zenvoice-hinglish-apex-ggml),
pinned to commit `0c540ce8945ef96b2880f2d2c0d05ba419621171`.

Hugging Face rather than a GitHub release, for two reasons that turned out to
matter. It fits the existing `{repo}/resolve/{revision}/{file}` URL shape, so
`downloadURL` and the `host == "huggingface.co"` assertion both stayed exactly
as they were — the provenance code did not have to be widened to accommodate
delivery. And a commit hash cannot be moved, where a release tag can be deleted
and re-pushed at different bytes.

Verified by downloading from the pinned URL and running *that* file, rather than
the local build, through the harness:

```
size   874,188,075   as declared
sha256 0b4324d2…c28c719   matches the catalog pin
result model hindi2hinglish-apex — 21/26 loanwords, 16.8% English
```

Only one verification rule changed: the license assertion accepts Apache-2.0
alongside MIT, plus a new assertion that `attribution` is non-empty, which is
the obligation that license carries. `ZenVoiceCoreChecks` is back to asserting
`allCases`, so a future capability cannot be added without a model behind it.

Also outstanding, unchanged from §5: VAD.

## 9. Beam search on Apex — tested, rejected

[§5](#5-carry-over-items-on-the-english-path) predicted the size-based beam
search gate would misclassify Apex: 874 MB puts it well above the 300 MB
ceiling, so it decodes greedy, while an 809 M model working in an
under-represented language is exactly where exploring alternatives should pay.
The specific hope was that it would recover `pull request`, which currently
comes back as `full request`.

Measured on 2026-07-25:

| | greedy | beam size 5 |
|---|---|---|
| English dictation WER | 16.8% | **15.5%** |
| Loanword preservation | 21/26 | 21/26 |
| Long-form insertions | clean | **invents 5 words (5.1%)** |
| Decode time, 12 clips | 11.60 s | 11.58 s |

**The prediction was wrong and the change is rejected.** Beam search did not
recover `pull request` or any other loanword — the score is unchanged and the
same five words are lost. It bought 1.3 points of English word error rate, which
Apex should not be used for anyway, and in exchange it started fabricating:
enough invented text on long-form to trip the harness's 5% insertion ceiling and
fail the run.

Invented words are the most dangerous failure a dictation tool has, because the
user may never notice text they did not say. That is not a trade worth 1.3
points, and the size-based gate turns out to be right about this model for the
wrong reason. The reasoning is recorded in `WhisperDecoding` so the experiment
is not repeated.

## 5. Carry-over items on the English path

Independent of Hinglish, found while reviewing current `main`:

**VAD is available and unused.** `Package.swift` pins whisper.cpp **v1.9.1**,
whose header exposes `whisper_full_params.vad`, `vad_model_path` and the whole
`whisper_vad_*` API. `WhisperTranscriber` sets none of it. Silero VAD is the
documented mitigation for Whisper's non-speech hallucination.

**Beam search is gated on file size, which is the wrong proxy.**
`WhisperDecoding.usesBeamSearch` enables beam search below 300 MB, on the
measured finding that it is worth ~3 points on Base and nothing on Medium or
Turbo. That measurement was taken on *English synthetic fixtures*. Two problems:
the conclusion has never been tested on Hindi, where decoder uncertainty is much
higher; and a 574 MB Apex q5_0 would be classified as "large, confident, skip
beam search" when it is an 809 M model in an under-represented language — the
case where beam search should help most.

**Turbo ships as q5_0.** [02 §3.3](02-research.md#33-stock-whisper-large-v3--large-v3-turbo)
warns that aggressive quantization disproportionately harms under-represented
languages. The catalog offers q5_0 only. q8_0 (874 MB for Apex) should be
available for multilingual profiles.
