# Update — July 2026

[02-research.md](02-research.md) called a Hinglish-native model "medium-high
risk, entirely on conversion", because no GGML build existed and the
safetensors→GGML path was a known rough edge. **That is no longer true.** This
document records what changed and what it means for the plan.

## 1. The blocker is gone, and there is a better model than the one we picked

Oriserve shipped **Whisper-Hindi2Hinglish-Apex** after our survey was written.
It is the same family as Prime but built on a different base:

| | Prime | **Apex** |
|---|---|---|
| Base model | whisper-large-v3 | **whisper-large-v3-turbo** |
| Parameters | 1,543.5 M | **808.9 M** |
| Downloads | 278.8 K | 151.9 K |
| License | Apache 2.0 | Apache 2.0 |
| Output script | Romanized Latin | **Romanized Latin** |

Apex is the right one for ZenVoice, not Prime. It is turbo-derived, so it lands
in the size and latency class we already ship and already recommend as the
default on Apple Silicon:

| Build | Size | Compare to catalog |
|---|---|---|
| `ggml-apex-hinglish-q5_0.bin` | 574 MB | `whisper-large-v3-turbo` q5_0 is 574,041,195 B |
| `ggml-apex-hinglish-q8_0.bin` | 874 MB | — |
| `ggml-apex-hinglish-fp16.bin` | 1.62 GB | — |

The q5_0 size matching our existing turbo entry almost exactly is the
confirmation that this is architecturally the same model we already run.

Reported WER against stock large-v3:

| Dataset | large-v3 | Apex | Prime |
|---|---|---|---|
| Common Voice | 61.94 | 35.96 | 32.43 |
| FLEURS | 50.84 | 29.79 | 28.68 |
| IndicVoices | 82.56 | 47.64 | 60.82 |

Prime is modestly better on the two clean benchmarks; Apex is **13 points
better on IndicVoices**, the hardest and most natural-speech of the three, at
half the parameter count. Trained on ~700 h of noisy Indian-accented Hindi.

### GGML conversions now exist

Three community conversions are published:

- [`Marquestra/Whisper-Hindi2Hinglish-Apex-GGML`](https://hf.co/Marquestra/Whisper-Hindi2Hinglish-Apex-GGML) — fp16 / q8_0 / q5_0
- [`voquill/whisper-hindi2hinglish-apex-ggml`](https://hf.co/voquill/whisper-hindi2hinglish-apex-ggml)
- [`curiophile/whisper-hindi2hinglish-ggml`](https://hf.co/curiophile/whisper-hindi2hinglish-ggml) — Prime

**Do not ship these directly.** All three report zero downloads and none is
from the model author. Their value is as *proof the conversion works* — the
risk [02 §4](02-research.md#4-integration-huggingface--whispercpp) was written
about has been retired by demonstration. Since the catalog pins `sha256` for
every model, ZenVoice should run the conversion itself and pin its own artifact
rather than trust an unattributed third party.

**Phase 2a therefore drops from a two-day spike with a real chance of failure
to a conversion run plus a catalog entry.**

## 2. The defect is still live

Re-ran `tools/translit-check.swift` on 2026-07-25 against current `main`:
still 8/8 wrong, still `computer → कंप्यूटर → kampyutara`. Nothing in the
intervening work touched `LocalTransliterator`, and Findings
[1](01-diagnosis.md#f1) and [2](01-diagnosis.md#f2) stand unchanged.

## 3. Mixed-script models — a second architecture worth knowing about

Two newer models emit **mixed script**: Hindi words in Devanagari, English
words left in Roman.

- [`Trelis/Whisper-Hinglish-Preview`](https://trelis.substack.com/p/whisper-hinglish)
  — injects a `<|mixedcode|>` token after the language token; without it the
  model collapses to a single script. Built on ArtPark's Vani base.
- [`shunyalabs/zero-stt-hinglish`](https://huggingface.co/shunyalabs/zero-stt-hinglish)
  — Whisper Medium post-trained, 0.8 B, Open RAIL license.

This is worth noting because of how it interacts with our code.
`LocalTransliterator.latinScript` already segments the string into native-script
runs and only transforms those. A mixed-script model would therefore have its
English words **pass through untouched** and only its Hindi words romanized —
[Finding 2](01-diagnosis.md#f2) would be fixed with no change to the
transliterator at all, leaving only the schwa/diacritic quality problem, which
is far more tractable once it is restricted to genuinely Hindi words.

It remains the fallback, not the plan. The `<|mixedcode|>` token is a custom
special token, and whisper.cpp's tokenizer handling of non-standard special
tokens is an unknown we would have to spike. Open RAIL is also a redistribution
question Apache 2.0 does not raise.

## 4. What must be measured before adopting Apex

The model card states no limitations at all, which is itself a reason for
caution. Specifically unverified:

- **English-dominant Hinglish.** Training data is Hindi-dominant. A technical
  user saying "the pull request ka status kya hai" is mostly English.
- **Pure English.** If a user leaves the Hinglish profile selected, output
  quality on English must not collapse.
- **Hallucination on silence**, which the noisy training data makes plausible.

### The harness cannot currently detect the bug it needs to detect

`ZenVoiceAccuracyChecks` asserts only that Hinglish output *contains no
Devanagari*. That is a property check, and it is passed equally by:

- `kampyutara par kama kara raha hum` — the current, broken output
- `computer par kaam kar raha hoon` — the desired output

Apex would pass it trivially on day one while telling us nothing. Before
adopting any Hinglish model the harness needs a **loanword-preservation rate**:
fixtures containing known English words, scored on whether those words come back
as English. That single metric captures [Finding 2](01-diagnosis.md#f2), which
is the defect that actually matters, and unlike WER it is not defeated by
Hinglish having no canonical spelling.

## 5. Carry-over items on the English path

Independent of Hinglish, found while reviewing current `main`:

**VAD is available and unused.** `Package.swift` pins whisper.cpp **v1.9.1**,
whose header exposes `whisper_full_params.vad`, `vad_model_path` and the whole
`whisper_vad_*` API. `WhisperTranscriber` sets none of it. Silero VAD is the
documented mitigation for Whisper's non-speech hallucination.

**Beam search is gated on file size, which is the wrong proxy.**
`WhisperDecoding.usesBeamSearch` enables beam search below 300 MB, on the
measured finding that it is worth ~3 points on Base and nothing on Medium or
Turbo. That measurement was taken on *English synthetic fixtures*. Two problems:
the conclusion has never been tested on Hindi, where decoder uncertainty is much
higher; and a 574 MB Apex q5_0 would be classified as "large, confident, skip
beam search" when it is an 809 M model in an under-represented language — the
case where beam search should help most.

**Turbo ships as q5_0.** [02 §3.3](02-research.md#33-stock-whisper-large-v3--large-v3-turbo)
warns that aggressive quantization disproportionately harms under-represented
languages. The catalog offers q5_0 only. q8_0 (874 MB for Apex) should be
available for multilingual profiles.
